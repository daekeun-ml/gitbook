# 03. 클러스터 구축 & 라이프사이클 스크립트

***

### 0. TL;DR

1. Slurm 클러스터도 EKS와 **같은 `sagemaker:CreateCluster` API**로 만들되, `Orchestrator`를 **`Slurm`** 으로. EKS는 `Orchestrator.Eks.ClusterArn`.
2. **VPC는 Slurm에선 선택**(미지정 시 platform VPC). 단 **FSx for Lustre를 붙이려면 직접 VPC**를 줘야 함.
3. **⚠️ 요즘 기본은 "스크립트 없이" 만드는 것**입니다(2025 하반기\~). 소프트웨어 설치 방식은 3가지 — **AMI 기반(신규 기본, 스크립트·S3 불필요) / Extension(`OnInitComplete`) / Custom(`OnCreate`, = 옛 레퍼런스 경로)**. `LifeCycleConfig`는 Extension·Custom에서만 필요(→ §2.1).
4. 노드 역할·파티션(**토폴로지**)을 정하는 방식도 2가지 — **API 기반 `SlurmConfig`(권장) vs 레거시 `provisioning_parameters.json`(S3 파일)**. 레거시 파일은 이제 **Custom 경로에서만** 등장(→ §2.2, §3). Continuous Provisioning은 **API 기반이 전제**(→ §5.1).
5. Day-2: `UpdateCluster`(스케일)·`UpdateClusterSoftware`(AMI 패치, 루트 볼륨 교체).

### 2. 클러스터 생성 (CLI)

> 📅 **먼저 알아둘 것 — 2026-02에 설정 방식이 크게 바뀌었습니다.** 원래 Slurm 클러스터는 **① S3에 올린 스크립트로 소프트웨어를 설치**하고 **② `provisioning_parameters.json`(S3 파일)으로 역할을 지정**하는 게 유일한 방법이었습니다. 2026-02-26 **"API-driven Slurm 설정"** 출시 이후로는 **① AMI가 스크립트 없이 자동 설치**하고 **② API(`SlurmConfig`)로 역할을 직접 지정**하는 게 **신규 권장 기본**이 됐습니다. 옛 방식(레거시)도 그대로 동작하지만, **블로그·워크샵 상당수가 아직 옛 방식**이라 헷갈리기 쉽습니다. 아래에서 두 방식을 나란히 정리합니다. (출처: [What's New 2026-02-26](https://aws.amazon.com/about-aws/whats-new/2026/02/amazon-sagemaker-hyperpod-slurm/) · [가이드](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html))

클러스터를 만들 때 정할 건 **딱 두 가지**뿐이고, 둘은 **서로 독립적**입니다(한쪽을 정해도 다른 쪽은 자유롭게 고름).

| 정할 것      | 질문                            | 선택지                         | 상세   |
| --------- | ----------------------------- | --------------------------- | ---- |
| **설치 방식** | 노드에 Slurm·Docker를 **어떻게 까나**  | AMI 기반 · Extension · Custom | §2.1 |
| **역할 지정** | 어느 그룹이 **컨트롤러·워커**인지 어떻게 알려주나 | API 기반 · 레거시 파일             | §2.2 |

> 🧭 **번호가 아니라 이름으로 기억하세요.** 두 축 모두 "1번/2번"이 아니라 **이름**(AMI 기반 / API 기반 …)으로 부릅니다. 설치 방식과 역할 지정은 **완전히 다른 축**이라 섞이지 않습니다.

두 축은 자유롭게 조합되지만, 현실에선 거의 아래 **두 조합** 중 하나입니다:

| 조합                                 | 설치 방식      | 역할 지정      | 언제                          |
| ---------------------------------- | ---------- | ---------- | --------------------------- |
| **신규 기본** (2025 하반기\~, **AWS 권장**) | **AMI 기반** | **API 기반** | 새로 만들 때. 스크립트·S3 불필요        |
| **옛 방식**                           | **Custom** | **레거시 파일** | 블로그·워크샵에 흔함. 기존 클러스터 (→ §3) |

> ⚠️ 오래된 자료 상당수가 "옛 방식"을 기본처럼 보여줍니다. **새로 만든다면 "신규 기본"** 을 쓰세요.

#### 2.1 설치 방식 — 노드에 소프트웨어를 어떻게 까나

노드가 부팅될 때 Slurm·Docker 등을 설치하는 방법이 3가지입니다.

> **비유** — 새 노트북을 받았을 때:
>
> * **AMI 기반** = 필요한 앱이 **이미 다 깔린 채로** 부팅 → 그대로 씀
> * **Extension** = 기본 세팅은 두고 **내 앱만 몇 개 추가**
> * **Custom** = **빈 노트북**을 받아 처음부터 내가 전부 세팅

| 방식                         | 하는 일                                             | S3·스크립트  | `LifeCycleConfig`                |
| -------------------------- | ------------------------------------------------ | -------- | -------------------------------- |
| **AMI 기반** (가장 단순, **권장**) | 부팅하면 Slurm·Docker·Enroot·Pyxis가 **알아서 깔림**       | ❌ 불필요    | **생략**                           |
| **Extension**              | AMI 기반 뒤에 **내 확장 스크립트** 실행(모니터링·LDAP 등)          | 확장 스크립트만 | `OnInitComplete` + `SourceS3Uri` |
| **Custom**                 | AMI 기반을 **건너뛰고** 내 스크립트가 설치·Slurm 시작까지 **전부** 담당 | 전체 세트    | `OnCreate` + `SourceS3Uri`       |

근거: [Slurm CLI 시작하기](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)의 "Node lifecycle configuration options" (AMI 기반이 권장 = _"we recommend starting with Option A, AMI-based configuration only"_).

> ⚠️ **예외는 EKS뿐입니다 — Continuous는 더 이상 예외가 아닙니다(2026-07 갱신).** 예전엔 "EKS·Continuous 둘 다 Custom(`OnCreate`)만 가능"이었지만, **AMI 기반 라이프사이클 설정이 Continuous Provisioning으로 확장**되면서(→ 09) 이 제약이 EKS에만 남았습니다. 현행 원문: _"Optional node lifecycle configuration is supported only for Slurm-orchestrated clusters. Amazon EKS-orchestrated clusters continue to require `LifeCycleConfig` with `OnCreate` and `SourceS3Uri` on every instance group."_ — [Slurm CLI 시작하기](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html). 즉 **Slurm이면 Continuous를 켜도 AMI 기반·Extension이 그대로 가능**합니다. (여전히 `OnCreate`와 `OnInitComplete`를 **한 그룹에 둘 다** 넣으면 validation 에러입니다.)
>
> ⚠️ **기존 클러스터는 AMI 호환성 게이트에 걸릴 수 있습니다.** 구버전 AMI로 만든 클러스터에서 `LifeCycleConfig`를 생략하면 검증 에러가 납니다: _"LifeCycleConfig is optional but requires a compatible AMI... Run UpdateClusterSoftware to update to an AMI that supports optional node lifecycle configuration."_ → 먼저 `update-cluster-software`로 최신 AMI를 적용해야 이 옵션이 먹힙니다.
>
> ⚠️ **문서 간 불일치 주의(라이브 확인일 2026-07 기준)**: Continuous 전용 문서(§5.1이 인용하는 `sagemaker-hyperpod-scaling-slurm.html`)의 예제는 **아직 옛 방식(`LifeCycleConfig`+`OnCreate`)만** 보여줍니다. 위 인용은 Slurm CLI 시작하기 가이드 쪽에서 확인된 것이라, 두 공식 문서가 서로 다른 최신성으로 보입니다 — 배포 전 현행 문서로 재확인 권장.

**예시 1 — AMI 기반 (가장 쉬움, 스크립트·S3 없이):** `LifeCycleConfig`를 아예 안 넣으면 됩니다.

```bash
aws sagemaker create-cluster --cli-input-json file://create_cluster.json
```

```json
{
  "ClusterName": "my-hyperpod-cluster",
  "Orchestrator": { "Slurm": { "SlurmConfigStrategy": "Managed" } },
  "InstanceGroups": [
    { "InstanceGroupName": "controller", "InstanceType": "ml.c5.xlarge", "InstanceCount": 1,
      "ExecutionRole": "arn:aws:iam::111122223333:role/HyperPodExecutionRole",
      "SlurmConfig": { "NodeType": "Controller" } },
    { "InstanceGroupName": "compute", "InstanceType": "ml.p5.48xlarge", "InstanceCount": 4,
      "ExecutionRole": "arn:aws:iam::111122223333:role/HyperPodExecutionRole",
      "ThreadsPerCore": 1,
      "SlurmConfig": { "NodeType": "Compute", "PartitionNames": ["train"] } }
  ]
}
```

> ℹ️ `LifeCycleConfig`가 없으니 **S3 버킷도, `provisioning_parameters.json`도 안 만들어도 됩니다.** 역할은 `SlurmConfig`로 정합니다(§2.2). FSx를 붙이면 마운트까지 자동입니다.
>
> **FSx를 붙이려면 (AMI 기반/Extension 경로)**: 인스턴스 그룹에 `InstanceStorageConfigs`로 명시합니다 — Custom(`OnCreate`) 경로의 `mount_fsx.sh` 하드코딩(§3.1)과 달리, 이 경로는 **API 필드**로 지정합니다.
>
> ```jsonc
> "InstanceStorageConfigs": [
>   { "FsxLustreConfig": {
>       "DnsName": "fs-0abc123def456789.fsx.us-west-2.amazonaws.com",
>       "MountPath": "/fsx",                 // 선택, 기본값 /fsx
>       "MountName": "abcdefgh" } }           // FSx 콘솔 또는 describe-file-systems로 확인
> ]
> ```
>
> FSx for OpenZFS는 `FsxOpenZfsConfig`(`DnsName`+`MountPath`, 기본 `/home`)로 별도 지정. **그룹당 Lustre 1개 + OpenZFS 1개까지**. FSx를 쓰려면 클러스터 레벨 `VpcConfig`도 필요(§1).
>
> **웹 콘솔에서 "그냥 클릭"하면?** **Quick setup** = AWS가 기본 스크립트를 대신 올려 씀 · **Custom setup → Lifecycle scripts = None** = AMI 기반. **어느 쪽도 `provisioning_parameters.json`을 직접 편집하지 않습니다.** (근거: [Slurm 콘솔 시작하기](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-console.html))

**역할을 정하는 두 방식 — API 기반 vs 레거시 파일**

Slurm 클러스터는 인스턴스 그룹마다 역할(**Controller / Login / Compute**)과 파티션이 있습니다. 이 **역할 정보를 어디에 적어두느냐**가 두 방식의 유일한 차이입니다.

|                                | **API 기반** (권장)                                                 | **레거시** (파일 기반)                         |
| ------------------------------ | --------------------------------------------------------------- | --------------------------------------- |
| 역할 정의 위치                       | 각 인스턴스 그룹의 **`SlurmConfig` 필드**                                 | **S3의 `provisioning_parameters.json`**  |
| 예                              | `"SlurmConfig": {"NodeType":"Compute","PartitionNames":["p1"]}` | `controller_group`, `worker_groups[]` 키 |
| 누가 역할을 읽나                      | **HyperPod 컨트롤 플레인**이 요청 시점에 이미 앎                               | 노드 부팅 시 **라이프사이클 스크립트**가 파일을 읽고 스스로 판단  |
| `provisioning_parameters.json` | **불필요**                                                         | **필수**                                  |
| Continuous Provisioning(§5.1)  | ✅ 필수 전제                                                         | ❌ 비호환                                   |

두 방식의 정의·비교는 [HyperPod references (Slurm 설정)](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-ref.html)의 "API-driven vs. legacy configuration"에, API 기반이 신규 권장이라는 점은 [라이프사이클 모범사례](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-lifecycle-best-practices-slurm.html)의 _"Option A: API-driven configuration (recommended)"_ 에 근거합니다.

**쉽게 말하면** — 신입사원 첫 출근에 비유하면, 레거시는 "책상 서랍의 안내문(S3 파일)을 열어봐야 내 직급을 아는" 방식이라 **인사팀(HyperPod)은 누가 팀장인지 모릅니다**. API 기반은 "채용 공고(API 요청)에 직급이 못박혀" 있어 **인사팀이 처음부터 압니다**. 이 차이가 Continuous Provisioning 호환성을 가릅니다(→ §5.1).

**실제로 어떻게 생겼나** — 같은 클러스터를 두 방식으로 적으면:

```jsonc
// 레거시 — create-cluster 요청엔 역할 정보가 없음 (그냥 인스턴스 그룹만)
{ "InstanceGroupName": "controller-machine", "InstanceType": "ml.c5.xlarge", "LifeCycleConfig": {...} }
// └ 역할은 별도 파일 s3://.../provisioning_parameters.json 안에 숨어 있음:
{ "controller_group": "controller-machine",
  "worker_groups": [ { "instance_group_name": "compute-nodes", ... } ] }
```

```jsonc
// API 기반 — 역할이 요청 안에 직접 박힘 → provisioning_parameters.json 자체가 불필요
{ "InstanceGroupName": "controller-machine", "InstanceType": "ml.c5.xlarge",
  "SlurmConfig": { "NodeType": "Controller" } }        // ← 역할이 여기 명시
```

> **왜 Continuous Provisioning은 API 기반이 필수인가 (핵심 인과):** Continuous의 본질은 **"컨트롤러부터 먼저 띄우고, 워커는 용량 생기는 대로 나중에 순차 투입"** 하는 우선순위 프로비저닝입니다. 그러려면 HyperPod가 **"누가 컨트롤러인지"를 미리** 알아야 순서를 정할 수 있어요.
>
> * **레거시**: 역할이 **노드가 부팅해서 S3 파일을 읽어야 비로소** 드러남 → HyperPod가 사전에 모름 → 순서를 못 정함 → **비호환**.
> * **API 기반**: HyperPod가 **요청 시점에 이미 앎** → "컨트롤러 먼저 → 나머지 async" 가능 → **성립**.
>
> 한 문장으로: _역할을 "부팅 스크립트가 판단"(레거시)_ vs _"AWS가 처음부터 앎"(API 기반)_ — Continuous는 후자여야만 우선순위 스케줄링이 되므로 마이그레이션을 요구합니다(에러 원문·마이그레이션 순서 → §5.1).

> ❓ **흔한 오해: "API 기반 = `Orchestrator`에 `SlurmConfigStrategy: Managed`를 주는 것"? — 다릅니다.** API 기반의 핵심은 **각 인스턴스 그룹의 `SlurmConfig` 필드**를 채우는 것입니다. `SlurmConfigStrategy`(`Managed`/`Merge`/`Overwrite`)는 **`slurm.conf`를 어떻게 관리할지**를 정하는 **별개** 파라미터고, ⚠️ **Continuous Provisioning에서는 값을 주면 API 에러**입니다(Continuous는 merge 모드 전용). 그래서 Continuous용 예제는 `"Orchestrator": {"Slurm": {}}`로 비워둡니다. 두 개념을 섞지 마세요.

> **왜 모든 인스턴스 그룹이 `ThreadsPerCore: 1`인가?** `ThreadsPerCore`는 물리 코어당 논리 스레드(vCPU) 수를 정하는 하이퍼스레딩(SMT) 스위치입니다 — **`1`=SMT 끔(코어=vCPU), `2`=SMT 켬(코어당 vCPU 2개)**, API 범위 1–2, 선택 필드. Slurm 레퍼런스는 컨트롤러·login·compute 전부 `1`로 둡니다. 무거운 연산은 GPU가 하고 CPU는 데이터 로딩·통신을 맡는데다, SMT를 끄면 두 스레드가 코어의 실행 유닛·캐시를 공유하며 생기는 성능 흔들림이 사라져 **코어 핀닝·NCCL/MPI 타이트 커플링의 예측성·재현성**이 좋아지기 때문입니다(AWS EC2도 HPC엔 SMT off 권장). CPU 전처리가 병목으로 _확&#xC778;_&#xB418;면 그때 `2`로 A/B 하세요.

> ❓ **흔한 오해: "`2`면 코어가 2배라 2배 빠르다"? — 아닙니다.** `2`는 물리코어를 늘리는 게 아니라 한 코어를 논리 vCPU 2개로 쪼개 많아 보이게 할 뿐이고, 두 스레드는 실행 유닛·캐시를 공유합니다. 그래서 연산으로 코어를 꽉 채우는 분산학습/HPC에선 이득이 거의 없고 경합으로 손해일 수도 있습니다. `ml.p5.48xlarge`는 `1`이어도 물리코어가 96개라 `DataLoader`에 충분합니다.

출처: [awsome-distributed-ai 5.sagemaker-hyperpod](https://github.com/awslabs/awsome-distributed-ai/tree/main/1.architectures/5.sagemaker-hyperpod) · [Slurm CLI 시작하기](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html)

### 3. 라이프사이클 스크립트 심화 (Custom 경로)

<figure><img src="../../.gitbook/assets/03-lifecycle-flow.png" alt=""><figcaption></figcaption></figure>

> ℹ️ **이 절은 §2.1의 Custom(`OnCreate`) 경로 이야기입니다.** AMI 기반/Extension을 쓰면 아래 대부분(Slurm 설치·`provisioning_parameters.json`)은 HyperPod가 대신 처리하므로 안 읽어도 됩니다. 기존 워크샵 재현·세밀 제어가 필요하거나, 예전 방식으로 만들어진 클러스터를 이해하려는 경우에 보세요.

과거 Slurm에서 EKS의 Helm 차트에 해당하던 것이 **라이프사이클 스크립트**입니다. 노드가 부팅될 때 HyperPod가 S3 스크립트를 받아 실행하며, 이게 Slurm을 설치·설정합니다. (지금은 AMI 기반이 이 일을 AMI에 내장해 자동화합니다.)

#### 3.1 실행 흐름

```
CreateCluster → 각 노드가 SourceS3Uri를 /tmp/<bucket>/로 다운로드 → on_create.sh(엔트리포인트) 실행
   on_create.sh: sleep 30(DNS) → SAGEMAKER_RESOURCE_CONFIG_PATH 해석 → python3 lifecycle_script.py
   lifecycle_script.py:
     ① provisioning_parameters.json + resource_config.json 읽기
     ② 내 IP로 소속 인스턴스 그룹 조회 → 그룹 이름으로 역할 결정(controller_group/login_group/그 외=compute)
     ③ 공통: install_ansible → mount_fsx.sh(/fsx) → add_users → wait_for_slurm_conf
     ④ 역할 분기:
        controller → setup_mariadb_accounting.sh(또는 multi_headnode_setup) → start_slurm.sh(slurmctld 기동)
        compute/login → start_slurm.sh(slurmd --conf-server <controller>, configless)
     ⑤ 선택: Docker+Enroot+Pyxis · 옵저버빌리티 · SSSD 등
```

* **`resource_config.json`**: HyperPod가 자동 생성(`/opt/ml/config/resource_config.json`, env `SAGEMAKER_RESOURCE_CONFIG_PATH`). ClusterArn·인스턴스 타입·**노드별 IP**를 담습니다. **내가 만들면 안 됩니다.**
* 노드 역할은 `resource_config.json`에서 내 IP가 속한 그룹의 **이름**을 `provisioning_parameters.json`의 `controller_group`/`login_group`과 비교해 결정됩니다.
* `/fsx`는 **하드코딩**: `mount_fsx.sh`를 `("/fsx")` 인자로 호출. (`mount_fsx.sh` 자체는 마운트 지점을 인자로 받지만, 호출하는 쪽이 `/fsx`로 고정)
* `slurm.conf`는 `/opt/slurm/etc/slurm.conf`. controller가 권위본을 만들고, compute는 `--conf-server`로 받아옵니다(configless).

#### 3.2 레거시 토폴로지 파일 — `provisioning_parameters.json`

> ℹ️ 이 파일은 **레거시 토폴로지 방식(Custom 경로에서 흔함)에서만** 씁니다. API 기반(§2.2, 권장)이면 **`SlurmConfig` 필드가 이 파일을 대체**하므로 만들 필요가 없습니다.

이 파일은 레포에 **커밋돼 있지 않습니다**. README 템플릿에서 만들어 S3에 (라이프사이클 스크립트와 **같은 폴더**에) 같이 올립니다.

```json
{
  "version": "1.0.0",
  "workload_manager": "slurm",
  "controller_group": "controller-machine",
  "login_group": "my-login-group",
  "worker_groups": [
    { "instance_group_name": "compute-nodes", "partition_name": "dev" }
  ],
  "fsx_dns_name": "fs-12345678a90b01cde.fsx.us-west-2.amazonaws.com",
  "fsx_mountname": "1abcdefg"
}
```

> ⚠️ **반드시 일치시킬 것**: `controller_group`과 `worker_groups[].instance_group_name`은 `cluster-config.json`의 `InstanceGroupName`과 **글자 그대로 일치**해야 합니다. `fsx_dns_name`/`fsx_mountname`은 실제 FSx Lustre와 일치. `login_group`은 선택(필수 아님). 위 키 셋은 **레포 README 템플릿(레거시 방식)** 기준입니다 — `validate-config.py`의 필수 키는 `version, workload_manager, controller_group, worker_groups, fsx_dns_name, fsx_mountname`. (참고: 최신 `lifecycle_script.py` 파서는 `slurm_configurations`로 파티션을 받는 경로도 있어, **API 기반 방식**을 쓰면 이 파일 자체가 불필요합니다 — §2.2.)

#### 3.3 커스터마이즈 — `config.py` 토글

```python
# LifecycleScripts/base-config/config.py (기본값)
enable_docker_enroot_pyxis = True   # Docker+Enroot+Pyxis 설치 (컨테이너 잡)
enable_observability       = False  # Prometheus/Grafana exporter (DIY 옵저버빌리티)
enable_sssd                = False  # LDAP/AD 통합
enable_fsx_openzfs         = False  # FSx OpenZFS를 /home에
enable_mount_s3            = False  # Mountpoint-S3
enable_slurm_log_rotation  = True
```

추가 커스터마이즈는 `utils/`에 스크립트를 두고 `lifecycle_script.py`에서 `ExecuteBashScript("./utils/yourscript.sh").run()`로 호출(README가 Miniconda 설치를 예로 듦).

### 5. 용량 옵션 & Day-2 운영

#### 5.1 용량 확보 & 프로비저닝 방식 — 별개의 두 축

여기서 헷갈리기 쉬운데, **"GPU 물량을 어디서 얻나"** 와 **"그 물량으로 클러스터를 어떻게 띄우나"** 는 **서로 다른 축**입니다.

| 축               | 질문                   | 선택지                                                                           |
| --------------- | -------------------- | ----------------------------------------------------------------------------- |
| **A. 용량 확보**    | GPU 물량을 어떻게 얻나       | **On-Demand**(그때그때 요청) / **Flexible Training Plans**(미래 용량 예약, 2024-12-04 GA) |
| **B. 프로비저닝 방식** | 확보한 물량으로 노드를 어떻게 띄우나 | 기본(all-or-nothing) / **Continuous**(부분 충원)                                    |

> 💡 즉 **Continuous Provisioning은 "세 번째 용량 옵션"이 아닙니다.** On-Demand·FTP로 확보한 물량을 **어떻게 프로비저닝하느냐**(다 모이면 한 번에 vs 잡히는 대로 순차)를 정하는 별개 스위치입니다. API 이름도 용량이 아니라 `NodeProvisioningMode`(노드 프로비저닝 모드)입니다 — CFN 원문: _"The mode for provisioning nodes... Continuous: Scaling behavior..."_. FTP로 예약한 용량이 조금씩 들어올 때 Continuous로 먼저 뜬 노드부터 굴리는 식으로 **두 축을 조합**합니다(→ 10 §6).

**프로비저닝 방식 — "다 모이면 시작"(기본) vs "온 사람부터 시작"(Continuous)**

**쉽게 말하면** — GPU 16대짜리 클러스터를 만든다고 해봅시다.

* **기본(all-or-nothing)**: 16대가 **전부 확보돼야** 클러스터가 뜹니다. 12대만 잡히고 4대가 용량 부족이면 → **전체 실패·롤백**. (회식에 예약 인원이 다 안 오면 아예 취소하는 격)
* **Continuous(`NodeProvisioningMode=Continuous`)**: 잡힌 노드부터 바로 `InService`로 굴리고, 못 잡은 나머지는 **백그라운드에서 계속 재시도**해 용량이 생기는 대로 합류시킵니다. (온 사람부터 식사 시작, 늦는 사람은 오는 대로 합류)
  * `MinInstanceCount`로 "최소 N대는 있어야 시작" 기준선을 정할 수 있고, 3시간 안에 못 채우면 롤백합니다.

> ⚠️ `Continuous`는 한때 EKS 전용이었으나 2026-03부터 Slurm도 지원합니다. 단 **CloudFormation 레퍼런스(**[**AWS::SageMaker::Cluster**](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/aws-resource-sagemaker-cluster.html)**)는 아직&#x20;**_**"This mode is only supported for EKS orchestrated clusters"**_**&#x20;로 남아 있어 stale**입니다. Slurm 지원은 개발자 가이드([Continuous provisioning, Slurm](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-scaling-slurm.html)) 기준으로 판단하세요.

**Continuous를 켜려면 — "API 기반" 클러스터여야 함**

Continuous는 **API 기반 Slurm 설정**(§2.2 — 그룹마다 `SlurmConfig` 필드로 역할 지정)에서만 켜집니다. 레거시(`provisioning_parameters.json`, S3 파일 기반) 클러스터에서 그냥 켜면 이 에러가 납니다:

```
ValidationException: Cluster must be on API-based Slurm configuration
before enabling Continuous Scaling
```

**마이그레이션 순서** (레거시 → Continuous):

<table><thead><tr><th width="103.6640625">단계</th><th>명령</th><th>하는 일</th></tr></thead><tbody><tr><td>1 (필요 시)</td><td><code>update-cluster-software</code></td><td>AMI/소프트웨어 최신화. ⚠️ 루트 볼륨 교체 → <strong>백업 먼저</strong>(§5.2)</td></tr><tr><td>2</td><td><code>UpdateCluster</code></td><td>그룹마다 <code>SlurmConfig</code>(<code>NodeType</code>/<code>PartitionNames</code>) 추가 → <strong>API 기반 전환</strong>(§2.2)</td></tr><tr><td>3</td><td><code>UpdateCluster</code></td><td><code>NodeProvisioningMode=Continuous</code> 켜기 (+ 원하면 <code>MinInstanceCount</code>)</td></tr></tbody></table>

> 💡 **라이프사이클 방식(§2.1)과는 별개 축입니다.** "API 기반이어야 한다"는 §2.2의 **역할 지정 방식** 얘기이고, **AMI 기반 라이프사이클 설정 자체는 2026-07\~ Continuous와 함께 쓸 수 있습니다**(§2.1의 "예외는 EKS뿐" 갱신 참고). 즉 Continuous + API 기반 역할지정 + AMI 기반 라이프사이클(스크립트 없이)을 **셋 다 동시에** 켤 수 있습니다. ⚠️ 다만 이 문서(Continuous 전용 가이드)의 공식 예제는 라이브 확인일(2026-07) 기준 아직 옛 `LifeCycleConfig`+`OnCreate` 방식만 보여주므로, 실제 조합 배포 전 현행 문서로 재확인하세요.

**⚠️ Continuous가 "포기하게 만드는" 것 3가지**

Continuous를 켜면 아래 기능들과 **동시에 쓸 수 없습니다**. 특히 멀티-헤드가 중요합니다.

| 함께 못 쓰는 것                  | 무슨 뜻                                                    |
| -------------------------- | ------------------------------------------------------- |
| **멀티-헤드 노드** (HA 컨트롤러)     | 컨트롤러를 2개 이상 두는 고가용성 구성                                  |
| **`SlurmConfigStrategy`**  | `slurm.conf`를 세밀 관리하는 옵션(`Managed`/`Merge`/`Overwrite`) |
| **온디맨드 deep health check** | 실행 중 노드 정밀 검사                                           |

> ❓ **흔한 오해: "멀티-헤드(HA 컨트롤러)라서 API 기반을 못 쓰는 거 아냐?" — 반대입니다.** 멀티-헤드 노드는 **원래 "API 기반"으로 설정하는 기능**이에요. 그러니 "멀티-헤드 때문에 API를 못 쓴다"가 아니라, **"멀티-헤드와 Continuous를 동시에 못 쓴다"** 가 정확합니다. 즉 HA 컨트롤러를 포기하지 않는 한, API 기반으로 옮겨도 Continuous는 안 켜집니다. **둘 중 하나만** 고르세요:
>
> * **(A) 멀티-헤드(HA) 유지** → Continuous 포기 (기존 all-or-nothing 방식 그대로)
> * **(B) Continuous 사용** → 컨트롤러 1개로 (멀티-헤드 포기)
>
> 근거(공식 문서 원문): _"The following features are not currently supported with continuous provisioning on Slurm clusters: **multi-head node configuration via API-based Slurm topology**, and `SlurmConfigStrategy`. Continuous provisioning operates exclusively in merge mode for `slurm.conf` management."_ — [Continuous provisioning 문서](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-scaling-slurm.html)의 **Prerequisites** 아래 Note.

> ❓ **흔한 오해: "그럼 `SlurmConfigStrategy`도 API 기반이니 같이 넣어야 하나?" — Continuous에선 넣으면 에러입니다.** Continuous는 `slurm.conf`를 **merge 모드로만** 다루기 때문에 `SlurmConfigStrategy`를 주면 API 에러가 납니다. 그래서 Continuous용 예제는 `"Orchestrator": {"Slurm": {}}`로 **비워둡니다**. ⚠️ 헷갈리기 쉬운데, **§2.2에서 채우는 `SlurmConfig`(그룹별 역할 필드)와 `SlurmConfigStrategy`(클러스터 레벨 옵션)는 이름만 비슷한 완전히 다른 것**입니다 — Continuous는 앞의 것(필수)만 쓰고 뒤의 것(금지)은 안 씁니다.
