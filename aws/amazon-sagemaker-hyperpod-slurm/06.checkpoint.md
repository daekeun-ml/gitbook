# 06. 체크포인트 & 스토리지 (Slurm)

***

### 0. TL;DR

1. **체크포인트는 "복원력의 마지막 단계"** — 05의 노드 자동 교체가 하드웨어를 살려줘도, **"이어서 학습"은 내 코드가 체크포인트를 로드**해야 성립합니다. **체크포인트는 전적으로 내 책임.**
2. **어디에**: 로컬 NVMe(`/opt/dlami/nvme`)는 **노드 교체 시 소실** → 체크포인트는 **반드시 `/fsx`(FSx Lustre) 또는 S3**(§3).
3. **무엇을**: 모델만이 아니라 **옵티마이저·LR 스케줄러·step·RNG 상태**까지 저장해야 "정확히 이어서"가 됩니다(§2).
4. **어떻게**: 대규모 분산은 **PyTorch DCP**(`torch.distributed.checkpoint`) — 랭크 병렬 저장 + **로드 시 리샤딩**(N노드 저장 → M노드 로드). **async 저장**으로 학습 멈춤(stall)을 줄입니다(§4).
5. **얼마나 자주**: **Young/Daly 직관** — 실패가 잦거나 체크포인트가 쌀수록 더 자주. async가 체크포인트 "비용"을 낮춰 **더 자주 떠도 손해가 적게** 만듭니다(§5).
6. **S3 자동화·리텐션**: `/fsx`에 자주 + **FSx↔S3 DRA**로 S3 자동 export + **last-N + 마일스톤** 로테이션으로 비용 관리(§7). ⚠️ DRA의 `DELETED` 이벤트는 `/fsx`에서 지운 걸 **S3까지 전파**하니 주의.

***

### 1. 왜 체크포인트가 goodput을 좌우하나

수천 GPU로 몇 주를 돌리면 하드웨어는 **반드시** 고장 납니다(05 §0). HyperPod가 결함 노드를 자동 교체해주지만, 그건 **"인프라를 되살리는" 데까지**입니다. 교체된 노드에서 **학습을 어디서부터 이어갈지**는 오로지 체크포인트가 결정합니다.

```
장애 → HyperPod가 노드 교체(자동) → 잡 재시작 → [ 마지막 체크포인트 로드 ] → 그 지점부터 학습
                                                        ↑ 이게 없으면 처음부터. 체크포인트 간격 = 날린 시간
```

* **체크포인트가 없으면**: 노드가 교체돼도 학습은 **step 0부터** 다시 → 수일치 계산이 증발.
* **체크포인트 간격이 너무 길면**: 마지막 체크포인트\~장애 시점 사이의 진행분이 날아감(= **lost work**).
* **체크포인트가 너무 잦거나 느리면**: 저장하느라 GPU가 노는 시간(= **stall/overhead**)이 커짐.

> 💡 **goodput = 전체 시간 중 "유효한 전진"에 쓴 비율.** 체크포인트 설계는 이 둘(lost work ↕ overhead)의 **트레이드오프 최적화**이고, §5의 주기 공식과 §4의 async 저장이 그 두 손잡이입니다.

### 2. 무엇을 체크포인트하나 — "모델만" 저장하면 안 됩니다

가장 흔한 실수: **모델 가중치만 저장.** 그러면 재개 시 옵티마이저 모멘텀·학습률 위치가 리셋돼 **loss가 튀거나 미묘하게 다른 궤적**을 그립니다. "정확히 이어서"를 원하면 **학습 상태 전체**를 저장하세요.

| 저장 대상                         | 왜 필요한가                     | 빠뜨리면              |
| ----------------------------- | -------------------------- | ----------------- |
| **모델 파라미터**                   | 당연                         | —                 |
| **옵티마이저 상태** (Adam moment 등)  | 모멘텀·2차 모멘트가 리셋되면 수렴 궤적이 바뀜 | loss 스파이크, 재수렴 지연 |
| **LR 스케줄러 상태**                | 학습률이 warmup/decay 중간값을 잃음  | 잘못된 LR로 재개        |
| **step / epoch 카운터**          | 데이터 위치·스케줄 기준점             | 같은 데이터 재학습 또는 건너뜀 |
| **RNG 상태** (torch/cuda/numpy) | dropout·데이터 셔플 재현성         | 완전한 결정적 재현 불가     |
| (선택) **데이터로더 상태**             | 정확한 샘플 위치 재개               | epoch 내 위치 어긋남    |

> ℹ️ PyTorch **DCP의 "Stateful 프로토콜"**(§4)을 쓰면, `state_dict()`/`load_state_dict()`를 구현한 객체(모델·옵티마이저 등)를 dict에 담아 **한 번에** 저장·복원할 수 있어 누락을 줄입니다. `get_state_dict(model, optimizers, ...)` 헬퍼가 모델+옵티마이저 state\_dict를 **짝으로** 뽑아줍니다.

### 3. 어디에 저장하나 — 노드 교체에서 살아남는 위치

| 위치                            | 노드 교체 시      | 속도           | 체크포인트 용도                 |
| ----------------------------- | ------------ | ------------ | ------------------------ |
| **로컬 NVMe** `/opt/dlami/nvme` | ❌ **소실**(휘발) | 가장 빠름        | 단독 사용 금지. (일시 staging에만) |
| **`/fsx`** (FSx for Lustre)   | ✅ 생존(별도 FS)  | 빠름(공유 병렬 FS) | ✅ **1차 저장소(권장)**         |
| **S3**                        | ✅ 생존(내구성 최고) | 느림(원격)       | ✅ **아카이브·원격 복제**         |

**핵심 규칙**: 05에서 본 대로 auto-resume은 하드웨어 결함 시 노드를 **교체**합니다. 로컬 NVMe에만 있던 체크포인트는 교체와 함께 사라지므로, **"이어서 학습"하려면 `/fsx`나 S3에서 로드**해야 합니다.

* `/fsx`는 라이프사이클 `lifecycle_script.py`가 `mount_fsx.sh`를 **`/fsx`** 인자로 호출해 전 노드에 마운트합니다(`noatime,flock,_netdev`, `<dns>@tcp:/<mountname>`). 같은 AZ 권장(cross-AZ 트래픽·비용 회피).
* 실전 패턴: **NVMe에 잠깐 staging → `/fsx`에 저장 → S3에 주기적 export**(§7). async 저장(§4)은 CPU 메모리에 staging하므로 NVMe를 꼭 거칠 필요는 없습니다.

### 4. 어떻게 저장하나 — PyTorch Distributed Checkpoint (DCP)

단일 GPU면 `torch.save`로 충분하지만, **FSDP/분산이면 DCP**(`torch.distributed.checkpoint`)가 표준입니다. DCP는 **여러 랭크가 병렬로** 저장·로드하고, **로드 시 리샤딩**을 처리합니다 — 즉 **N개 노드에서 저장한 체크포인트를 M개 노드로 로드**할 수 있어(노드 수가 바뀌는 auto-resume과 궁합이 좋음), 토폴로지에 얽매이지 않습니다.

> ⚠️ **버전 주의**: 아래 API는 **PyTorch 2.x**(검증 기준 2.12) 기준입니다. 특히 **`async_save`는 공식적으로 "experimental and subject to change"** 이고 일부 옵션(`DefaultStager`/`AsyncSaveResponse`)은 **2.9+** 입니다. 배포 전 **클러스터에 설치된 torch 버전**으로 시그니처를 확인하세요.

#### 4.1 기본 저장·로드 (동기)

```python
import torch.distributed.checkpoint as dcp
from torch.distributed.checkpoint.state_dict import get_state_dict, set_state_dict

# 저장 — 모델+옵티마이저 state_dict를 짝으로 추출해 랭크 병렬 저장
model_sd, optim_sd = get_state_dict(model, optimizers=optimizer)
state = {"model": model_sd, "optim": optim_sd, "step": step, "sched": scheduler.state_dict()}
dcp.save(state, checkpoint_id=f"/fsx/ckpt/step-{step}")     # → Metadata 반환

# 로드 — in-place. 각 랭크가 자기 샤드만 읽고, 리샤딩 자동 처리
state = {"model": model_sd, "optim": optim_sd, "step": 0, "sched": scheduler.state_dict()}
dcp.load(state, checkpoint_id="/fsx/ckpt/step-1000")        # state를 제자리에서 채움(반환 None)
set_state_dict(model, optimizer, model_state_dict=state["model"], optim_state_dict=state["optim"])
```

> ⚠️ **`dcp.save`/`dcp.load`가 현행 API입니다.** 예전 `save_state_dict`/`load_state_dict`는 **deprecated**("switch to save/load") — 옛 예제를 복붙하지 마세요. ℹ️ **FSDP state\_dict 종류**: `FULL_STATE_DICT`(rank 0에 통합, 메모리 부담 큼) vs `SHARDED_STATE_DICT`(랭크별 샤드 유지). 대규모는 **sharded**가 정석 — `get_state_dict`/`set_state_dict`를 쓰면 이 토글을 수동으로 만질 필요가 줄어듭니다.

#### 4.2 async 저장 — 학습 멈춤(stall) 줄이기

동기 저장은 저장이 끝날 때까지 GPU가 놉니다. **`dcp.async_save`** 는 state\_dict를 **staging 저장소(기본 CPU 메모리)로 복제한 뒤, 별도 스레드에서 디스크에 씁니다** → GPU는 디스크 쓰기를 기다리지 않고 학습을 재개.

```python
checkpoint_future = None
for step in range(num_steps):
    train_step(...)
    if step % fsx_freq == 0:
        # 직전 async 저장이 끝났는지 확인(권장: 동시 1개만)
        if checkpoint_future is not None:
            checkpoint_future.result()
        model_sd, optim_sd = get_state_dict(model, optimizers=optimizer)
        state = {"model": model_sd, "optim": optim_sd, "step": step, "sched": scheduler.state_dict()}
        checkpoint_future = dcp.async_save(state, checkpoint_id=f"/fsx/ckpt/step-{step}")  # → Future[Metadata]
```

> ⚠️ **오해 주의 — async라고 GPU가 0초만 멈추는 게 아닙니다.** 기본 `async_save`는 **① GPU→CPU 복제(이 구간은 blocking)** → ② CPU→디스크 쓰기(비동기)입니다. 즉 **①의 staging 시간만큼은 학습이 멈춥니다.** (PyTorch 블로그 예시: 7B 모델 GPU→CPU stage가 \~6–14초, 전체 다운타임이 동기 대비 크게 감소 — "7B 모델 148.8초 → 6.3초, 약 23배"라고 소개. **이 수치는 PyTorch가 제시한 예시이지 HyperPod 보장값이 아닙니다.**) CPU 복제까지 학습과 겹치려면 **`DefaultStager`(2.9+)** 가 필요합니다. ℹ️ **권장: 동시 async 요청 1개** — PyTorch 권고 _"limiting checkpoints to one asynchronous request at a time"_ (메모리 압박 회피). 마지막 체크포인트 뒤에는 반드시 future를 `.result()`로 마감하세요. ℹ️ **SageMaker Model Parallel(SMP)** 을 쓰면 자체 async API(`torch.sagemaker.distributed.checkpoint`의 `async_save`, `maybe_finalize_async_calls`)도 있습니다.

#### 4.3 노드 교체에 안전한 재개

재개 엔트리포인트는 05 §3.2처럼 `scontrol`로 노드 목록·MASTER\_ADDR를 **다시 계산**한 뒤, `/fsx`의 **가장 최근 유효 체크포인트**를 찾아 `dcp.load`하도록 작성합니다. DCP의 리샤딩 덕에 교체로 노드 수가 달라져도 로드됩니다.

### 5. 얼마나 자주 저장하나 — 주기 튜닝

"자주 저장 = 안전하지만 느림 / 드물게 = 빠르지만 위험"의 트레이드오프입니다. HPC에는 이걸 정량화한 고전 결과가 있습니다.

**Young/Daly 최적 주기 (1차 근사)**:

```
최적 체크포인트 간격  T_opt ≈ √(2 · C · μ)
   C = 체크포인트 1회 비용(저장에 드는 시간),  μ = 평균 무장애 시간(MTBF)
```

직관은 단순합니다:

* **실패가 잦을수록(μ↓) → 더 자주** 저장 (T\_opt↓).
* **체크포인트가 쌀수록(C↓) → 더 자주** 저장해도 손해가 적음.

> 📖 이건 AWS 기능이 아니라 **일반 HPC 복원력 이론**입니다(Young 1974, Daly 2006; `T_opt ≈ √(2μC)`는 μ가 C·복구시간보다 충분히 클 때의 1차 근사). AWS 문서엔 이 공식이 없으니 "가이드가 참고로 제시하는 원리"로 보세요. 실제 μ·C는 클러스터·모델마다 다르니 **측정해서 대입**하세요.

**여기서 §4 async가 왜 중요한가**: async 저장은 **유효 비용 C(=학습이 멈추는 stall 시간)를 낮춥니다**(총 바이트나 MTBF를 바꾸는 게 아님). C가 작아지면 위 공식상 **같은 낭비율로 더 자주 저장**할 수 있어, "자주 저장해 lost work를 줄이면서도 overhead는 낮게"가 가능해집니다.

> 💡 **실무 시작점**: async 저장을 켜고, `/fsx`엔 상대적으로 자주(예: 수십 분\~수 step 단위), S3엔 드물게(마일스톤). 그런 다음 실제 저장 시간(C)과 장애 빈도(μ)를 관측해 간격을 조정하세요. (아래 수치는 예시 자리표시자이지 권장 상수가 아닙니다.)

### 6. FSx 처리량 사이징 — 체크포인트가 병목이 안 되게

체크포인트 저장이 느리면 C가 커지고(§5) goodput이 떨어집니다. FSx for Lustre 처리량은 **용량에 비례**합니다:

```
FSx 총 처리량(MB/s) = 스토리지 용량(TiB) × PerUnitStorageThroughput(MB/s/TiB)
   예) 4.8 TiB × 50 MB/s/TiB = 240 MB/s 베이스라인
```

* **PERSISTENT\_2 SSD 티어**: 125 / 250 / 500 / 1000 MB/s/TiB. (PERSISTENT\_1 SSD: 50/100/200 · SCRATCH\_2: 200 고정)
* **체크포인트 쓰기 창(window) 사이징 (파생 산술, AWS 미공개 공식)**: 목표 저장 시간이 `t`초, 체크포인트 크기가 `S` GB면 필요 처리량 ≈ `S/t` (GB/s). `용량(TiB) × 티어(MB/s/TiB) ≥ 필요치`가 되도록 용량·티어를 고릅니다.
  * 예: 300 GB 체크포인트를 \~30초에 쓰려면 ≈ 10 GB/s → 그만한 aggregate 처리량이 나오도록 사이징. (읽기가 캐시에 있으면 네트워크 바운드, 쓰기·미캐시 읽기는 디스크 바운드.)
* ⚠️ **EFA 활성 SSD 파일시스템은 생성 후 처리량 변경 불가** — 처음 사이징이 중요.

> 상세한 FSx 클래스·메타데이터 IOPS·스트라이핑(PFL)·사이징 매트릭스는 HyperPod 스토리지 추천 전략 §6에 있습니다. 여기선 "체크포인트 관점"만 짚었습니다.

### 7. S3 자동 내보내기(DRA) + 리텐션/로테이션

`/fsx`는 빠르지만 용량·비용 한계가 있고, S3는 내구성·저비용 아카이브에 좋습니다. **FSx↔S3 Data Repository Association(DRA)** 로 `/fsx`에 쓴 체크포인트를 **자동으로 S3에 export**할 수 있습니다.

```bash
aws fsx create-data-repository-association \
  --file-system-id fs-0abc... \
  --file-system-path /ckpt/ \
  --data-repository-path s3://my-bucket/checkpoints/ \
  --s3 'AutoExportPolicy={Events=[NEW,CHANGED]}'      # ← DELETED 포함 여부 신중히(아래 주의)
```

* **동작**: `/fsx/ckpt/`의 새/변경 파일을 앱이 파일을 닫은 뒤 **비동기로** S3에 push. import-only / export-only / 양방향 설정 가능.
* **기본값 함정**: **콘솔은 자동 import·export가 기본 ON, CLI/API는 기본 OFF.** CLI로 만들면 명시해야 합니다.
* **제약**: 파일시스템당 **최대 8개 DRA**. **FSx Lustre 2.10·Scratch 1 미지원**. export 객체는 **S3 Standard** 클래스로 저장.

> ⚠️ **오해 주의 — `DELETED` 이벤트 = 위험한 양날의 검.** `AutoExportPolicy`에 `DELETED`를 넣으면 **`/fsx`에서 파일을 지울 때 S3의 대응 객체도 자동 삭제**됩니다. 체크포인트 **로테이션(오래된 것 삭제)** 용도로 `/fsx`를 청소하면 **S3 아카이브까지 날아갑니다.** 아카이브를 보존하려면 `DELETED`를 빼고(`Events=[NEW,CHANGED]`) S3 리텐션은 **S3 라이프사이클 정책**으로 따로 관리하세요. ℹ️ **`CHANGED` 는 in-place 패치가 아니라 "삭제 후 재생성"** 입니다(메타데이터만 바뀌어도 재생성). 큰 체크포인트를 자주 덮어쓰면 export 트래픽이 커질 수 있습니다. ⚠️ **FS/DRA 삭제 전** `AgeOfOldestQueuedMessage`(CloudWatch) 지표가 0인지 확인 — 아직 export 안 된 변경분이 있으면 유실됩니다.

**리텐션·로테이션 모범 사례** (프레임워크 레벨, 아래 mechanics는 프레임워크 문서로 재확인 권장):

* **last-N + 마일스톤**: 최근 N개만 `/fsx`에 유지(빠른 재개용) + 일정 간격(예: 매 epoch/일정 step)의 **마일스톤은 S3에 영구 보관**. 스토리지 비용을 bound.
* `/fsx` 청소는 **DRA `DELETED` 없이** 하고, S3 쪽은 라이프사이클으로 오래된 마일스톤을 Glacier 등으로 이전.
* 저장 실패를 놓치지 않게 **FSx data repository 이벤트 로깅을 CloudWatch Logs로** 켜두세요.

### 8. 모범 사례 체크리스트

* [ ] 체크포인트를 **`/fsx` 또는 S3**에 저장 (로컬 NVMe 단독 ❌ — 노드 교체 시 소실).
* [ ] **모델뿐 아니라 옵티마이저·스케줄러·step·RNG** 저장 (§2) — "정확히 이어서".
* [ ] 분산이면 **DCP `dcp.save`/`dcp.load`** + **sharded** state\_dict. 옛 `save_state_dict`(deprecated) 금지.
* [ ] **`async_save`로 stall 감소** — 단 GPU→CPU staging 구간은 여전히 blocking임을 인지, torch 버전 확인(experimental).
* [ ] async는 **동시 1개**만, 마지막에 `.result()`로 마감.
* [ ] 재개 엔트리포인트가 `scontrol`로 토폴로지 재계산 후 **최신 유효 체크포인트** 로드 (05 §3.2).
* [ ] **주기**: async 켜고 `/fsx` 자주 + S3 마일스톤 드물게 → 실제 C·μ 측정해 조정 (§5).
* [ ] **FSx 처리량**을 체크포인트 크기/목표 시간에 맞춰 사이징 (§6). EFA-SSD는 사후 변경 불가.
* [ ] **S3 export**는 DRA(`NEW,CHANGED`), **로테이션 시 `DELETED` 주의** (§7).
* [ ] FS/DRA 삭제 전 `AgeOfOldestQueuedMessage=0` 확인.

### 9. ⚠️ Managed Tiered Checkpointing은 EKS 전용

EKS 가이드의 그 기능(CPU RAM 1차 + RDMA peer 복제 + S3 2차, `amzn-sagemaker-checkpointing` 라이브러리 + `TieredStorageConfig`)은 **Slurm에 없습니다**:

* dev guide가 "**PyTorch frameworks on Amazon EKS HyperPod clusters**"로 명시, 전제조건이 EKS 클러스터 + EKS OIDC IAM, 활성 CLI가 `--orchestrator "Eks={ClusterArn=...}"`.
* GA(2025-09-08) What's New: "currently available for SageMaker HyperPod clusters using the **EKS orchestrator**."

→ Slurm에서 비슷한 "메모리 계층 + S3" 효과를 원하면 **§4 async(CPU staging) + §7 DRA(S3 export)** 를 직접 조합하는 게 현재의 방법입니다.
