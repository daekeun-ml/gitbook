# 07. 옵저버빌리티 & CLI 운영 (Slurm)

***

### 0. TL;DR

1. **클러스터 운영 CLI는 `aws sagemaker`(boto3)** — `create-cluster`/`update-cluster`/`update-cluster-software`/`list-cluster-nodes` 등. **`hyp` CLI는 EKS 전용**이라 Slurm 클러스터를 관리하지 않습니다.
2. **잡/노드 모니터링은 Slurm 네이티브** — `squeue`/`sinfo`/`scontrol`/`sacct`.
3. **메트릭 옵저버빌리티는 DIY** — 라이프사이클 `enable_observability=True`로 DCGM exporter·EFA node exporter·Slurm exporter·Prometheus를 노드에 설치하고, **Amazon Managed Prometheus(AMP) + Managed Grafana(AMG)** 를 직접 연결. (EKS의 1-click 애드온 같은 매니지드 통합 아님)
4. **구성은 4단계**: ① AMP/AMG CFN 스택 배포 → ② `enable_observability=True` → ③ head Prometheus 검증 → ④ AMG 대시보드 연결. **가장 잘 정리된 실습 가이드는** [**`awslabs/awsome-distributed-ai`의 4.prometheus-grafana**](https://github.com/awslabs/awsome-distributed-ai/tree/main/4.validation_and_observability/4.prometheus-grafana) (§4 상세).
5. **⚠️ 순서**: observability **CFN 스택이 항상 먼저** 존재해야 함(라이프사이클 `install_prometheus.sh`가 스택 출력을 읽음). 신규·기존 클러스터 모두 붙일 수 있고, 기존 클러스터는 `update-cluster-software`로 라이프사이클 재실행 — 이건 **재부팅이 아니라 루트 볼륨 교체**라 `/fsx`는 생존하지만 로컬 디스크는 초기화·잡은 중단됨(백업 필수, → §4.4).
6. **CloudWatch 메트릭**(CPU/GPU/메모리·노드 수)은 `/aws/sagemaker/Clusters` 네임스페이스에 기본 on(2024-12-13\~) — 이건 별도 설정 없이 항상 켜져 있음.

***

### 1. 왜 Slurm은 EKS처럼 "1-click"이 안 되나? (먼저 이해하기)

같은 HyperPod인데 EKS 모드는 콘솔에서 버튼 하나(1-click 애드온)로 끝나고, Slurm 모드는 왜 CFN 스택 + 라이프사이클을 손으로 엮어야 할까요? **답은 "오케스트레이터가 있느냐 없느냐"입니다.**

#### 쉬운 비유

* **EKS 모드 = 관리인(쿠버네티스)이 상주하는 건물.** 새 장비(exporter)를 들이려면 관리인에게 "이거 모든 층에 설치해줘"라고 표준 양식(DaemonSet/Helm/애드온)으로 지시하면 알아서 배포·재시작·복구합니다. AWS는 그 표준 양식 위에 **애드온 하나**를 얹기만 하면 되니 1-click이 가능합니다.
* **Slurm 모드 = 관리인이 없는 건물.** 장비를 설치할 "표준 배포 시스템"이 애초에 없습니다. 그래서 **노드가 부팅될 때 실행되는 설치 스크립트(라이프사이클 스크립트)** 에 "이 노드엔 이걸 깔아라"를 직접 적어두는 방식으로 대신합니다.

#### 기술적으로 (핵심 3가지)

|                | EKS 모드                                               | Slurm 모드                                                           |
| -------------- | ---------------------------------------------------- | ------------------------------------------------------------------ |
| **배포 표준**      | 쿠버네티스가 exporter를 **DaemonSet**(노드마다 자동 1개)으로 배포·자가복구 | 그런 계층이 **없음** → 부팅 시 **라이프사이클 스크립트**가 Docker로 설치                   |
| **AMP/AMG 연결** | 애드온이 **remote\_write·IAM·데이터소스까지 자동 배선**             | **CFN 스택으로 직접** AMP/AMG 생성 + `install_prometheus.sh`가 스택 출력을 읽어 배선 |
| **대시보드**       | 사전 구축 대시보드 5종 **자동 생성**                              | 커뮤니티 대시보드 5종을 **직접 import**(ID로)                                   |

* 한 줄 요약: **EKS는 "쿠버네티스"라는 자동 배포 엔진이 있어서 AWS가 애드온으로 감쌀 수 있고, Slurm은 그 엔진이 없어서 "부팅 스크립트 + CFN 스택"으로 사람이 조립**합니다. → 부품(exporter·Prometheus·AMP·AMG)과 최종 그림은 **똑같고**, 조립을 자동으로 하느냐 손으로 하느냐만 다릅니다.
* 좋은 소식: 라이프사이클 스크립트가 exporter·Prometheus **설치**는 자동화해 주므로, 실제 사람이 하는 일은 **① CFN 스택 배포 + ② `enable_observability=True` + ③ Grafana 대시보드 import** 세 가지뿐입니다(→ §4).

> 자매 문서 EKS 옵저버빌리티 §2 "왜 1-click 애드온이 고마운가"와 대조해서 보면 차이가 선명합니다. EKS는 이 조립을 애드온이 대신하고, Slurm은 여러분이 합니다.

### 2. 클러스터 운영 — `aws sagemaker` (hyp CLI 아님)

```bash
# 클러스터/노드 조회
aws sagemaker list-clusters
aws sagemaker describe-cluster --cluster-name ml-cluster
aws sagemaker list-cluster-nodes --cluster-name ml-cluster
aws sagemaker describe-cluster-node --cluster-name ml-cluster --node-id i-0abc...

# 스케일 / 패치 / 삭제
aws sagemaker update-cluster --cli-input-json file://update_cluster.json
aws sagemaker update-cluster-software --cluster-name ml-cluster   # 루트 볼륨 교체, 백업 먼저
aws sagemaker delete-cluster --cluster-name ml-cluster            # controller는 단독 삭제 불가
```

> ⚠️ **`hyp` CLI / Python SDK(`sagemaker-hyperpod`)는 EKS/Kubernetes 전용**입니다(training-job = `HyperPodPyTorchJob` CRD, inference endpoint = K8s CRD). Slurm 클러스터는 위 `aws sagemaker`(또는 boto3)로 관리하고, 잡은 노드에서 Slurm 명령으로 다룹니다.

출처: [Slurm 운영 CLI](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-operate-slurm-cli-command.html) · [hyp CLI(EKS 전용)](https://github.com/aws/sagemaker-hyperpod-cli)

### 3. 잡 / 노드 모니터링 — Slurm 네이티브

```bash
# (로그인/컨트롤러 노드에서, SSM 접속 후)
squeue                       # 큐·실행 중 잡
squeue -u $USER
scontrol show job <jobid>    # 잡 상세
sinfo -a -N -l               # 노드·파티션 상태(idle/mix/drain/down/fail)
scontrol show node=<ip>      # 노드 상세
sacct -j <jobid> --format=JobID,JobName,State,Elapsed,MaxRSS,ReqGRES   # 어카운팅(완료 잡)
```

* **`sacct`/어카운팅**: controller의 `slurmdbd` + MariaDB(또는 RDS)로 자동 구성(라이프사이클 `setup_mariadb_accounting.sh`/`setup_rds_accounting.sh`). 잡별 자원 사용·과금 집계.
* **거버넌스**: Slurm에선 **파티션·QOS·fair-share**가 EKS Task Governance(Kueue)의 역할을 합니다(Slurm 네이티브).

출처: [Slurm 잡 실행/모니터링](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-run-jobs-slurm.html)

### 4. 메트릭 옵저버빌리티 — DIY (Prometheus + Grafana)

#### 4.0 쉽게 말하면 (그림 한 장)

```
 [Compute 노드]                    [Head(controller) 노드]        [AWS 매니지드]
  DCGM exporter (GPU)  ─┐
  EFA node exporter    ─┼──scrape──►  Prometheus  ──remote_write──►  AMP  ──►  AMG
  (CPU/메모리/디스크)    ─┘             + Slurm exporter              (저장)   (대시보드)
```

* **Exporter = 노드에서 숫자를 뱉는 작은 프로그램**(HTTP로 `/metrics` 노출). GPU·네트워크·Slurm 상태를 각각 담당.
* **Prometheus = 그 숫자를 주기적으로 긁어(scrape) 모으는 수집기.** head 노드에서 돎.
* **AMP(Amazon Managed Prometheus) = 매니지드 저장소.** head의 Prometheus가 여기로 `remote_write`(밀어넣기).
* **AMG(Amazon Managed Grafana) = 대시보드.** AMP를 데이터소스로 붙여 그래프를 봄.
* 핵심: **EKS는 콘솔에서 1-click 애드온**이지만, **Slurm은 이 파이프라인을 직접 조립**합니다. 다만 라이프사이클 스크립트가 exporter+Prometheus 설치는 자동화해 주므로, 실제로 손이 가는 건 "AMP/AMG를 미리 만들어두는 것" 뿐입니다.

#### 4.1 구성 4단계 (AWS 공식 흐름)

**① 사전 준비 (AMP·AMG 프로비저닝) — 클러스터 만들기&#x20;**_**전**_**에**

* **실행 역할(AmazonSagemakerClusterExecutionRole)에 관리형 정책 2개 부착**:
  * `AmazonPrometheusRemoteWriteAccess` — head Prometheus가 AMP로 밀어넣기(`aps:RemoteWrite`).
  * `AWSCloudFormationReadOnlyAccess` — 라이프사이클 스크립트가 스택 출력(AMP URL·Region)을 읽기 위함.
* **IAM Identity Center 활성화** (AMP·AMG 인증에 필수 전제).
* 샘플 CloudFormation 스택 **`cluster-observability.yaml`** 배포(README의 **1-Click Deploy** 버튼) → **AMP 워크스페이스 + AMG 워크스페이스** + IAM 역할을 한 번에 생성.
  * 스택 **출력값(AMPRemoteWriteURL·Region)** 을 ②의 `install_prometheus.sh`가 AWS CLI로 자동 회수.
* ⚠️ **IAM Identity Center를 못 쓰는 환경**이면 대안 스택 **`cluster-observability-os-grafana.yaml`**(오픈소스 self-managed Grafana) 사용 → `README-OS-grafana.md`.

```bash
# 가장 잘 정리된 가이드 (awslabs/awsome-distributed-ai)
# 4.validation_and_observability/4.prometheus-grafana/
#   ├─ README.md                        ← 메인(AMG + IAM Identity Center)
#   ├─ README-OS-grafana.md             ← 대안(오픈소스 Grafana)
#   ├─ README-grafana-alerts.md         ← 알림 설정
#   ├─ cluster-observability.yaml       ← CFN 스택 (AMP+AMG+역할)
#   ├─ cluster-observability-os-grafana.yaml
#   ├─ 1click-dashboards-deployment/    ← 대시보드 자동 배포
#   └─ dcgm-metrics.csv                 ← DCGM 지표 목록
```

**② Exporter + Prometheus 설치 — `enable_observability=True` 한 줄**

* 라이프사이클 `config.py`에서 **`enable_observability = True`** 로만 바꾸면 됩니다. 나머지는 `lifecycle_script.py`가 노드 타입별로 자동 설치:

```python
# lifecycle_script.py (발췌) — enable_observability=True 일 때 실행
if Config.enable_observability:
    if node_type == SlurmNodeType.COMPUTE_NODE:      # 워커 노드
        ExecuteBashScript("./utils/install_docker.sh").run()
        ExecuteBashScript("./utils/install_dcgm_exporter.sh").run()      # GPU
        ExecuteBashScript("./utils/install_efa_node_exporter.sh").run()  # 고속망+CPU/메모리
    if node_type == SlurmNodeType.HEAD_NODE:         # 컨트롤러 노드
        wait_for_scontrol()
        ExecuteBashScript("./utils/install_docker.sh").run()
        ExecuteBashScript("./utils/install_slurm_exporter.sh").run()     # Slurm 메트릭
        ExecuteBashScript("./utils/install_prometheus.sh").run()         # 수집기
```

* ⚠️ **모든 exporter·Prometheus는 Docker 컨테이너로 설치**됩니다 → 그래서 head·compute 양쪽에 `install_docker.sh`도 함께 돎.
* head의 `install_prometheus.sh`가 **AMP로 `remote_write`** 하도록 ①에서 받은 remote-write URL로 설정됩니다(실행 역할에 `aps:RemoteWrite` 권한 필요).

> **❓ "CFN 스택으로 AMP/AMG 생성 + `install_prometheus.sh`가 스택 출력을 읽어 배선"이 무슨 뜻?** 이 한 줄에 두 동작이 들어 있습니다.
>
> **(1) "CFN 스택으로 AMP/AMG 생성"** — AMP·AMG 워크스페이스를 콘솔에서 손으로 만들 수도 있지만, IAM 역할·권한까지 일일이 엮어야 합니다. 대신 **CloudFormation 템플릿(`cluster-observability.yaml`) 하나를 배포하면 AMP + AMG + IAM 역할이 한 번에** 만들어집니다. EKS 애드온처럼 자동이 아니라 **이 스택을 내가 배포**해야 해서 "직접"입니다.
>
> **(2) "스택 출력을 읽어 배선"** — head의 Prometheus가 지표를 AMP로 보내려면(`remote_write`) **AMP 주소(URL)를 알아야** 하는데, 이 URL은 스택을 만들어봐야 정해집니다(계정·리전마다 다름 → 스크립트에 하드코딩 불가). CloudFormation은 스택 생성 후 **출력값(Outputs)** 으로 이 값들을 내놓습니다:
>
> ```
> [CFN 스택 배포] → Outputs:
>    AMPRemoteWriteURL = https://aps-workspaces.<region>.amazonaws.com/workspaces/ws-xxxx/api/v1/remote_write
>    Region            = us-east-1
> ```
>
> 그러면 head 노드 부팅 때 `install_prometheus.sh`가 **① AWS CLI로 그 Outputs를 조회**(그래서 실행 역할에 `AWSCloudFormationReadOnlyAccess` 필요) → **② 읽은 URL·Region을 `/etc/prometheus/prometheus.yml`의 `remote_write` 자리에 채워 넣습니다**:
>
> ```yaml
> remote_write:
>   - url: <AMPRemoteWriteURL 자동 주입>
>     sigv4: { region: <Region 자동 주입> }   # SigV4 서명으로 AMP 인증
> ```
>
> 이 "**스택이 뱉은 주소를 스크립트가 읽어 설정 파일에 꽂아 Prometheus↔AMP를 연결**"하는 것이 **배선(wiring)** 입니다.
>
> **비유**: CFN 스택 배포 = 창고(AMP)·모니터실(AMG)을 짓고 **주소 쪽지(Outputs)** 를 받음 → `install_prometheus.sh` = 택배기사(Prometheus)가 그 쪽지를 읽어 배송지 설정에 창고 주소를 적음 → 이제 지표가 자동으로 그 창고로 배송. **창고가 먼저 있어야 주소를 읽으니, 스택이 항상 먼저**(→ §4.4).

> **❓ 흔한 오해: "Docker로 설치"가 내 노트북/로컬에서 Docker를 만든다는 뜻?** — **아닙니다.**
>
> * **어디서**: 여기서 "노드"는 내 로컬이 아니라 **AWS에 떠 있는 HyperPod GPU 서버들**입니다.
> * **언제**: 라이프사이클 스크립트는 **각 노드가 부팅될 때 SageMaker가 자동 실행**하는 "입주 체크리스트"입니다(클러스터 생성 시, 또는 노드 교체 시). 내가 SSH로 돌리는 게 아닙니다.
> * **"Docker로"의 의미**: exporter(DCGM·EFA·Slurm)들을 노드에 직접 깔면 버전·의존성 충돌이 나기 쉬워, **컨테이너로 감싸 한 줄로 실행**합니다. 그 전제로 노드 안에서 `install_docker.sh`가 **Docker 엔진부터** 깔고 → 각 exporter를 `docker run`으로 띄웁니다.
> * **내가 하는 일**: `enable_observability=True` + S3 업로드 + (기존 클러스터면) `update-cluster-software`뿐. **`docker build`·이미지 푸시·로컬 Docker 설정은 전혀 없습니다** — 컨테이너 설치·실행은 부팅 시 노드가 알아서 합니다.

**③ 검증 — head 노드에서 Prometheus 확인**

* head 노드(SSM 접속)에서 Prometheus가 떠 있고 타깃(compute exporter들)을 정상 scrape 하는지, AMP로 remote-write가 나가는지 확인. (공식 "Validating Prometheus setup" 절차)

**④ 대시보드 — AMG 워크스페이스 연결**

* AMG 워크스페이스에서 **AMP를 데이터소스로 추가** → GPU/EFA/Slurm 대시보드로 시각화. IAM Identity Center 사용자로 로그인.

#### 4.2 어떤 노드에 무엇이 설치되나

| Exporter / 수집기        | 설치 노드       | 무엇을 노출                                                          |
| --------------------- | ----------- | --------------------------------------------------------------- |
| **DCGM exporter**     | Compute(워커) | GPU 온도·전력·사용률·XID 오류·NVLink                                     |
| **EFA node exporter** | Compute(워커) | 고속망 RX/TX·RDMA **+ CPU·메모리·디스크** (Prometheus node\_exporter 포크) |
| **Slurm exporter**    | Head(컨트롤러)  | 큐·파티션·노드 상태·잡 통계(어카운팅)                                          |
| **Prometheus**        | Head(컨트롤러)  | 위 exporter들을 scrape → AMP로 remote\_write                        |

> 참고: 공식 문서는 CPU/메모리/디스크 지표를 **EFA node exporter(node\_exporter 포크)** 가 함께 담당한다고 명시합니다(별도 순정 node\_exporter를 따로 두는 구성이 아님).

#### 4.4 ⚠️ 순서 — 클러스터 먼저? observability 먼저?

**결론: 둘 다 가능. 신규 클러스터든 이미 떠 있는 클러스터든 붙일 수 있습니다.** repo README 원문: _"If you have already created your HyperPod cluster, you can follow these instructions to update your existing HyperPod cluster with Observability."_

**단, 불변 규칙 하나** — **observability CFN 스택(AMP+AMG)은 라이프사이클 스크립트가 실행되기&#x20;**_**전**_**에 반드시 존재**해야 합니다. `install_prometheus.sh`가 스택 출력(remote-write URL·Region)을 AWS CLI로 읽어 `prometheus.yml`을 작성하기 때문입니다. 즉 "스택 → (그 뒤) exporter/Prometheus 설치" 순서는 항상 고정.

| 시나리오             | 순서                                                                                                                                                 |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| **신규 클러스터**      | ① IAM 정책 2개 부착 → ② CFN 스택 배포 → ③ `config.py` `enable_observability=True` + S3 업로드 → ④ **클러스터 생성**(라이프사이클이 exporter/Prometheus 설치·remote\_write 배선) |
| **이미 떠 있는 클러스터** | ① CFN 스택 배포(아직 없으면) → ② `config.py` 수정 후 S3 재업로드 → ③ **`aws sagemaker update-cluster-software`** 로 라이프사이클 재실행                                      |

* 반대로 "클러스터를 먼저 띄우고 스택 없이 라이프사이클만 `enable_observability=True`로 돌리면" `install_prometheus.sh`가 읽을 스택 출력이 없어 remote\_write 설정이 비게 됩니다 — 그래서 **스택이 항상 먼저**입니다.

**❓ "그럼 노드를 재부팅해야 하나?" — 아니요, 재부팅이 아니라 루트 볼륨 교체입니다**

`update-cluster-software`는 "노드를 껐다 켜는(reboot)" 게 아니라, **각 인스턴스의 루트 볼륨(OS 디스크)을 최신 AMI로 갈아끼우고 부팅하면서 라이프사이클 스크립트를 다시 실행**합니다. 그래서 이 참에 `enable_observability=True`가 반영돼 exporter·Prometheus가 새로 깔리는 것입니다.

* **무엇이 살고 무엇이 사라지나** (이게 핵심):
  * ✅ **`/fsx`(FSx for Lustre)는 별도 파일시스템이라 그대로 생존** — 코드·데이터·**체크포인트**는 안전.
  * ❌ **루트 볼륨·로컬 NVMe(`/opt/dlami/nvme`)는 초기화/소실** — 여기에만 둔 데이터는 날아갑니다.
  * ⚠️ controller의 `/var/spool/slurmctld`·MariaDB 등 **로컬 상태는 미리 백업** (repo의 `patching-backup.sh`).
* **잡은 중단됩니다** — 볼륨을 갈아끼우므로 그 인스턴스 그룹의 실행 중 잡은 끊깁니다. → **먼저 잡을 드레인하거나 체크포인트를 `/fsx`·S3에 저장한 뒤** 패치하세요.
* **전체가 동시에 죽지는 않음 (롤링 가능)** — `DeploymentConfig`로 **롤링 배치 크기·대상 인스턴스 그룹 지정·알람 기반 자동 롤백**을 줄 수 있어, 한 번에 일부 노드씩 교체해 가용성을 유지할 수 있습니다. **API/CLI 전용**(콘솔 없음).
* 참고: 결함 노드를 고칠 때 쓰는 `reboot`(같은 호스트 재기동)과 혼동하지 마세요 — 그건 05 복원력의 자동 노드 복구 얘기고, **소프트웨어 패치(`update-cluster-software`)는 항상 루트 볼륨 교체 방식**입니다.

> 요약: **"재부팅"이 아니라 "루트 볼륨 교체 + 라이프사이클 재실행"**. `/fsx`는 살지만 로컬 디스크는 초기화되고 잡은 끊기니, **체크포인트 백업 → (가능하면) 롤링 배치로 패치**가 정석입니다. (→ 03 §5.2 스케일 & 패치·06 체크포인트)
