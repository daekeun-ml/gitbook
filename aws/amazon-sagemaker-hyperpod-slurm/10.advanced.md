# 10. 고급 시나리오 (Advanced)

***

### 0. TL;DR

1. **멀티-헤드 노드**(§2): 컨트롤러를 **1 주 + N 백업**으로 두는 HA 구성. 주 컨트롤러가 죽으면 백업이 **자동 승격**(failover). 컨트롤러 그룹 `InstanceCount≥2`로 켜고, RDS(MariaDB)·FSx·Secrets Manager·SNS가 상태를 외부화. **컨트롤러는 최소 1개**(0으로 축소 불가). **Slurm 전용**.
2. **Multi-AZ**(§3): 인스턴스 그룹별 `OverrideVpcConfig`로 서로 다른 AZ의 서브넷/SG를 지정. 용량 확보엔 유리하나 **cross-AZ 트래픽·FSx 지연** 주의(대규모 통신은 단일 AZ 권장).
3. **Enroot/Pyxis 심화**(§4): 기본은 04 §4. 여기선 **프라이빗 ECR 인증·`.sqsh` 캐싱·`/var/log/aws/clusters` 필수 마운트·멀티노드 rendezvous** 등 실전 함정.
4. **`SlurmConfigStrategy`**(§5): API 기반 클러스터에서 `slurm.conf` 관리 방식 — **`Managed`(기본, 드리프트 감지)·`Overwrite`·`Merge`**. 드리프트 감지는 **파티션 설정에만** 적용. **Slurm 전용**, Continuous에선 금지(→ §6).
5. **용량 전략**(§6): **FTP**(미래 용량 예약) + **Continuous**(부분 용량 즉시 시작) + **MinCount**(최소 대수 게이트). FTP와 Continuous는 **상보적**. 단 Continuous를 켜면 §2 멀티-헤드·§5 `SlurmConfigStrategy`·온디맨드 deep health check를 **포기**.
6. ⚠️ **가장 중요한 상호배타**: **멀티-헤드(HA) ↔ Continuous Provisioning은 동시 사용 불가**. HA가 필요하면 Continuous를 포기해야 합니다(→ §7 매트릭스).

***

### 2. 멀티-헤드 노드 — HA 컨트롤러

#### 2.1 왜 필요한가

기본 Slurm 클러스터는 **컨트롤러(헤드) 노드가 1개**입니다. 이 노드의 `slurmctld`가 죽으면 **스케줄링·잡 관리가 전부 멈춥니다**(단일 장애점, SPOF). 수 주짜리 대규모 잡이나 여러 팀이 공유하는 프로덕션에서는 이게 치명적이죠.

**멀티-헤드 = 컨트롤러를 여러 개**(1 주 + N 백업) 두는 고가용성 구성입니다. 백업이 주 컨트롤러를 **상시 감시**하다가, 주가 죽거나 응답이 없으면 **백업 하나가 자동으로 새 주 컨트롤러로 승격**합니다.

> **쉽게 말하면** — 은행 지점장(주 컨트롤러)이 자리를 비우면 **부지점장(백업)이 즉시 대행**하는 것. 대행이 가능하려면 장부·금고 열쇠가 **개인 서랍이 아니라 공용 금고**에 있어야 합니다 → 그래서 상태를 RDS·FSx·Secrets Manager로 **외부화**합니다.

**언제 쓰나:**

* 수 주\~수개월 장기 대규모 학습 — 컨트롤러 다운이 전체 잡을 위협
* 여러 팀 공유 프로덕션 클러스터 — 다운타임 비용이 큼
* Slurm 어카운팅 DB·설정을 **직접 통제**하고 싶을 때

#### 2.2 아키텍처 — 무엇이 엮이나

```
        ┌───────── 상시 감시 ─────────┐
   [주 컨트롤러]  ←───────────────→  [백업 컨트롤러(N)]     slurmctld: 1 active + N standby
        │  주 다운 시 자동 승격         │                    slurmdbd: 어카운팅
        └───────────┬─────────────────┘
       ┌────────────┼───────────────────────────┐  (주·백업이 공유)
  [FSx for Lustre]      [RDS for MariaDB]     [Secrets Manager]
   Slurm 설정·런타임 상태   어카운팅(잡기록·과금)    RDS 자격증명
                          [SNS] → 컨트롤러 ON/OFF 시 관리자 알림
       [컴퓨트 노드(slurmd)] ← 주 컨트롤러 지시로 잡 실행
```

| 서비스                 | 역할                     | 왜                                |
| ------------------- | ---------------------- | -------------------------------- |
| **FSx for Lustre**  | Slurm 설정·런타임 **상태** 저장 | 주·백업이 **같은 상태**를 봐야 매끄러운 인계      |
| **RDS for MariaDB** | 어카운팅 DB(잡 기록·과금) 외부화   | 컨트롤러가 죽어도 기록 보존                  |
| **Secrets Manager** | RDS 자격증명 보관            | FSx/컨트롤러의 안전한 DB 접근              |
| **SNS**             | 컨트롤러 ON/OFF 알림         | failover 발생을 관리자가 즉시 인지 (**선택**) |
| **IAM**             | 컨트롤러용·컴퓨트용 **역할 2개**   | 권한 분리                            |

#### 2.3 설정 흐름 (CloudFormation 2스택)

멀티-헤드는 **라이프사이클 스크립트 기반**(§03의 ③ Custom 경로)으로 설정합니다. AMI 기반 원클릭이 아닙니다.

```bash
# 1) 기본 리소스 스택 (VPC·서브넷·FSx·컴퓨트 실행역할·S3·SG)  — 주/백업 서브넷을 서로 다른 AZ로
aws cloudformation deploy --template-file sagemaker-hyperpod.yaml --stack-name sagemaker-hyperpod \
  --parameter-overrides PrimarySubnetAZ=use1-az4 BackupSubnetAZ=use1-az1 --capabilities CAPABILITY_IAM

# 2) 멀티-헤드 추가 리소스 스택 (컨트롤러 실행역할·RDS MariaDB·SNS·Secrets Manager)
aws cloudformation deploy --template-file sagemaker-hyperpod-slurm-multi-headnode.yaml --stack-name sagemaker-hyperpod-mh \
  --parameter-overrides SlurmDBSecurityGroupId=$SECURITY_GROUP SlurmDBSubnetGroupId1=$PRIMARY_SUBNET \
  SlurmDBSubnetGroupId2=$BACKUP_SUBNET SNSSubEmailAddress=$EMAIL SlurmDBUsername=$DB_USER_NAME \
  --capabilities CAPABILITY_NAMED_IAM        # ← 명명된 IAM 역할 생성이라 NAMED_IAM 필요

# 3) 실행 역할에 정책 attach → 4) 라이프사이클 스크립트 + provisioning_parameters.json S3 업로드 → 5) create-cluster
```

컨트롤러 HA는 **컨트롤러 인스턴스 그룹의 `InstanceCount`를 2 이상**으로 주어 켭니다 (별도 "백업 개수" 필드는 없음 — 백업 = `InstanceCount` − 1):

```json
{ "InstanceGroupName": "controller-machine", "InstanceType": "ml.t3.medium",
  "InstanceCount": 2, "ThreadsPerCore": 1 }
```

`provisioning_parameters.json`의 `slurm_configurations` 블록이 멀티-헤드 배선을 담습니다:

```jsonc
"slurm_configurations": {
  "slurm_database_secret_arn": "$SLURM_DB_SECRET_ARN",      // Secrets Manager
  "slurm_database_endpoint":   "$SLURM_DB_ENDPOINT_ADDRESS", // RDS MariaDB
  "slurm_shared_directory":    "/fsx",
  "slurm_database_user":       "$DB_USER_NAME",
  "slurm_sns_arn":             "$SLURM_SNS_FAILOVER_TOPIC_ARN"  // 선택: 없으면 SNS 알림 미설정
}
```

#### 2.4 운영 제약 (검증됨)

* **컨트롤러 최소 1개** — 원문: _"the minimum number of controller nodes you can scale down to is 1. This means that you cannot scale down the number of controller nodes to 0."_ `batch-delete-cluster-nodes`로도 **모든 컨트롤러 삭제는 불가**.
* HA/failover엔 **컨트롤러 `InstanceCount≥2`** 필요(1 주 + ≥1 백업). 1개면 자동 failover 없음.
* **SNS는 선택** — `slurm_sns_arn`을 안 주면 알림을 설정하지 않음.
* ⚠️ **2025-01-24 이전 생성 클러스터**는 `update-cluster`/`batch-delete-cluster-nodes` 전에 **`UpdateClusterSoftware` 먼저** 실행해야 함.
* 생성은 최대 15분 소요.
* **단일 → 멀티 컨트롤러 마이그레이션**: 기존 컨트롤러 그룹을 `worker_groups`로 옮기고 **새 `controller_group` 이름을 추가**한 뒤 `update-cluster` 실행(문서 notes 페이지).

> ❓ **흔한 오해: "멀티-헤드는 EKS에도 있겠지?" — 아닙니다, Slurm 전용입니다.** EKS는 쿠버네티스 **제어 평면을 AWS가 관리**하므로 고객이 만지는 컨트롤러 노드 자체가 없습니다. 멀티-헤드(고객 관리 컨트롤러의 HA)는 **Slurm에만** 존재합니다. 모든 멀티-헤드 문서 페이지 제목이 _"...for a SageMaker HyperPod Slurm cluster"_ 입니다.

출처: [멀티-헤드 개요](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-multihead-slurm.html) · [멀티-헤드 설정](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-multihead-slurm-setup.html)

### 3. Multi-AZ 클러스터

#### 3.1 왜 / 어떻게

대규모 GPU(P5 등)는 **단일 AZ에서 원하는 수량이 안 잡힐 때**가 많습니다. Multi-AZ는 인스턴스 그룹마다 **다른 AZ의 서브넷/보안그룹**을 지정해 가용성을 넓히는 구성입니다.

기본은 클러스터 레벨 `VpcConfig` 하나(단일 AZ)지만, 인스턴스 그룹 스펙의 **`OverrideVpcConfig`** 로 그룹별 서브넷/SG를 **오버라이드**해 여러 AZ에 분산합니다.

```jsonc
{ "InstanceGroupName": "compute-az1", "InstanceType": "ml.p5.48xlarge", "InstanceCount": 8,
  "OverrideVpcConfig": { "Subnets": ["subnet-az1-xxxx"], "SecurityGroupIds": ["sg-xxxx"] } }
```

* 앞서 본 **멀티-헤드**(§2.3)도 주/백업 컨트롤러를 **다른 AZ**(`PrimarySubnetAZ`/`BackupSubnetAZ`)에 두는 게 권장 — 즉 HA와 Multi-AZ는 함께 갑니다.
* **IPv6 동작이 오케스트레이터별로 다름**(검증됨): **Slurm은 노드에 IPv6+IPv4 dual-stack을 자동 구성**해 즉시 IPv6 통신 가능. EKS는 dual-stack 주소를 받되 **Pod의 IPv6는 EKS 클러스터가 명시적으로 IPv6-enabled일 때만** 가능.

#### 3.2 ⚠️ 트레이드오프 — 공짜가 아니다

> ❓ **흔한 오해: "Multi-AZ면 무조건 좋다"? — 대규모 통신엔 오히려 독일 수 있습니다.** AZ가 다르면 노드 간 트래픽이 **AZ를 넘나들어**(cross-AZ) 지연·비용이 늘고, **FSx for Lustre는 같은 AZ 권장**(03 §1)이라 cross-AZ 마운트는 성능이 떨어집니다. NCCL 타이트 커플링 분산학습은 **단일 AZ + 클러스터 배치**가 정석입니다. Multi-AZ는 **"용량을 못 잡을 때의 확장 카드"** 이지 기본값이 아닙니다.

출처: [ClusterInstanceGroupSpecification (OverrideVpcConfig/IPv6)](https://docs.aws.amazon.com/sagemaker/latest/APIReference/API_ClusterInstanceGroupSpecification.html) · [전제조건(멀티 AZ)](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-prerequisites.html)

### 4. Enroot/Pyxis 컨테이너 심화

> ℹ️ **기본**(변환·`.sqsh`·Pyxis 플래그·`config.py` 토글)은 04 §4에 있습니다. 여기선 **실전에서 막히는 지점**만 다룹니다.

#### 4.1 NVMe 루트 경로 — 안 잡으면 디스크 풀

신선한 인스턴스의 루트는 `/tmp`(EBS 100GB)뿐이라, **큰 LLM 컨테이너를 import하면 금방 꽉 찹니다.** P·G 계열의 **로컬 NVMe**(`/opt/dlami/nvme`)를 Docker/Enroot 루트로 써야 합니다. 라이프사이클 스크립트가 자동 설정하지만, **반드시 확인**:

```bash
srun -N 8 cat /etc/enroot/enroot.conf | grep ENROOT_RUNTIME_PATH
# → ENROOT_RUNTIME_PATH  /opt/dlami/nvme/tmp/enroot/user-$(id -u)   (8노드 모두 이래야 정상)
srun -N 8 cat /etc/docker/daemon.json
# → {"data-root": "/opt/dlami/nvme/docker/data-root"}
```

#### 4.2 프라이빗 ECR 인증 + `.sqsh` 빌드

프라이빗 ECR(예: SMP·DLC 이미지)을 쓰려면 **실행 역할에 ECR 권한**을 주고, 로그인 후 import합니다:

```bash
# IAM 실행 역할에 추가: ecr:BatchGetImage, ecr:GetDownloadUrlForLayer, ecr:GetAuthorizationToken,
#                       ecr:BatchCheckLayerAvailability, ecr-public:* (필요 시)
aws ecr get-login-password --region us-west-2 \
  | docker login --username AWS --password-stdin 658645717510.dkr.ecr.us-west-2.amazonaws.com
docker build -t smpv2 .
enroot import -o smpv2.sqsh dockerd://smpv2:latest      # → .sqsh를 /fsx에 두면 전 노드 공유·재사용
```

> 💡 `.sqsh`를 `/fsx`에 한 번 만들어 두면 노드마다 다시 import할 필요가 없어 **잡 시작이 빨라집니다**(오픈소스 이미지는 인증 불필요).

#### 4.3 ⚠️ HyperPod 필수 마운트 — `/var/log/aws/clusters`

컨테이너로 학습할 때 **호스트의 `/var/log/aws/clusters`를 컨테이너에 마운트**해야 합니다. 안 하면 HyperPod가 클러스터 검증을 못 합니다(복원력 기능에 영향):

```bash
: "${HYPERPOD_PATH:="/var/log/aws/clusters":"/var/log/aws/clusters"}"   # Enroot 마운트 변수
```

#### 4.4 멀티노드 컨테이너 학습 패턴

`srun --container-image`에 마운트를 걸고, `torchrun`은 Slurm rendezvous로 묶습니다:

```bash
#SBATCH --nodes=8
#SBATCH --exclusive
declare -a ARGS=( --container-image $IMAGE
                  --container-mounts $HYPERPOD_PATH,$CHECKPOINT_PATH,/fsx/data:/fsx/data )
declare -a TORCHRUN=( --nproc_per_node=8 --nnodes=$SLURM_JOB_NUM_NODES
                      --rdzv_id=$SLURM_JOB_ID --rdzv_backend=c10d --rdzv_endpoint=$(hostname) )
# EFA/NCCL env
export NCCL_ASYNC_ERROR_HANDLING=1 FI_EFA_USE_DEVICE_RDMA=1 NCCL_SOCKET_IFNAME="^lo,docker" \
       RDMAV_FORK_SAFE=1 CUDA_DEVICE_MAX_CONNECTIONS=1
srun -l "${ARGS[@]}" torchrun "${TORCHRUN[@]}" train.py --checkpoint_dir $CHECKPOINT_DIR
```

출처: [Slurm 컨테이너(Enroot/Pyxis)](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-run-jobs-slurm-docker.html) · [SMPv2 예제(awsome-distributed-training)](https://github.com/aws-samples/awsome-distributed-training/tree/main/3.test_cases/17.SM-modelparallelv2)

### 5. `slurm.conf` 드리프트 관리 — `SlurmConfigStrategy`

#### 5.1 무엇 / 왜

API 기반 토폴로지(03 §2.2)를 쓰면, HyperPod가 각 그룹의 `SlurmConfig`를 컨트롤러의 **`slurm.conf` 파티션 설정으로 번역**해 씁니다. 그런데 관리자가 컨트롤러에 SSH로 들어가 `slurm.conf`를 **손으로 고치면**(드리프트), API가 생각하는 상태와 어긋납니다. `SlurmConfigStrategy`는 **이 상황을 어떻게 처리할지**를 정합니다.

`Orchestrator.Slurm` 아래 클러스터 레벨 필드입니다:

```jsonc
"Orchestrator": { "Slurm": { "SlurmConfigStrategy": "Managed | Overwrite | Merge" } }
```

| 전략                 | 드리프트 감지                                      | 수동 편집             | 용도                  |
| ------------------ | -------------------------------------------- | ----------------- | ------------------- |
| **`Managed`** (기본) | **켜짐** — 드리프트 있으면 `UpdateCluster` **실패(에러)** | 미지원               | 단일 진실 원천            |
| **`Overwrite`**    | 꺼짐                                           | **덮어씀**(수동 편집 폐기) | 드리프트에서 복구·초기 상태로 리셋 |
| **`Merge`**        | 꺼짐                                           | **보존·병합**         | 커스텀 `slurm.conf` 유지 |

#### 5.2 놓치기 쉬운 포인트

* **`Managed`가 기본** — `Orchestrator.Slurm`을 생략해도 Managed로 동작(드리프트 감지 on).
* **언제든 변경 가능** — 원문: _"You can change SlurmConfigStrategy at any time using UpdateCluster. There is no lock-in."_
* **컨트롤러 손 튜닝을 하려면 `Merge`** — `Managed`는 손 편집이 있으면 업데이트를 막습니다.

> ❓ **흔한 오해: "`Managed`면 내 `slurm.conf` 수정을 전부 감시·차단한다"? — 파티션 설정만입니다.** 검증된 원문: _"Drift detection applies **only to Slurm partition configuration** in slurm.conf... Changes to other slurm.conf settings, such as scheduling parameters, resource limits, or accounting configuration, are **not monitored**."_ 즉 스케줄러 파라미터·리소스 제한 등은 감지 대상이 아니고, **파티션-노드 매핑**만 봅니다.

> ⚠️ **Continuous를 켜면 이 절 전체가 무효**입니다. Continuous는 `slurm.conf`를 **merge 모드로만** 다루고 `SlurmConfigStrategy`를 주면 **API 에러**입니다(→ §6.4, §7). `SlurmConfigStrategy`는 **Slurm 전용**(EKS엔 `slurm.conf` 자체가 없음).

출처: [Slurm CLI 시작하기(SlurmConfigStrategy 표)](https://docs.aws.amazon.com/sagemaker/latest/dg/smcluster-getting-started-slurm-cli.html) · [HyperPod references(Slurm 설정)](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-ref.html)

### 6. 용량 & 프로비저닝 전략 — FTP + Continuous + MinCount

대규모 GPU는 "원하는 때 원하는 수량"을 잡기 어렵습니다. 세 도구를 조합해 해결하는데, **세 도구는 서로 다른 축**입니다 — 하나(FTP)만 "용량 확보"이고, 나머지 둘은 "그 용량을 어떻게 띄우나"입니다.

#### 6.1 세 도구의 역할 (축이 다름)

| 도구                                | 축                                | 한 줄                                  | 비유            |
| --------------------------------- | -------------------------------- | ------------------------------------ | ------------- |
| **Flexible Training Plans (FTP)** | 용량 확보                            | 미래 시점의 GPU를 **예약 블록**으로 확보           | 식당 **단체석 예약** |
| **Continuous Provisioning**       | 프로비저닝 방식(`NodeProvisioningMode`) | 다 안 모여도 **잡힌 노드부터 시작**, 나머지 async 충원 | 온 사람부터 식사 시작  |
| **MinCount** (`MinInstanceCount`) | Continuous의 옵션                   | "**최소 N대** 있어야 시작" 게이트               | 최소 정족수        |

> 💡 즉 **Continuous·MinCount는 "용량을 더 얻는" 도구가 아닙니다.** 용량은 On-Demand/FTP로 얻고, Continuous는 그 용량으로 **클러스터를 어떻게 띄우나**(부분 충원)를 정하는 별개 스위치입니다(→ 03 §5.1).

#### 6.2 FTP — 미래 용량 예약

* 흐름: `SearchTrainingPlanOfferings`(검색) → `create-training-plan`(선불 결제) → `Scheduled` → 블록 시작 시 `Active`.
* 예약 단위: **1\~182일**(1일 단위), 수량 **1/2/4/8/16/32/64**, **최대 8주(56일) 전** 예약.
* 지원 인스턴스: p4d/p5/p5e/p5en/p6-b200/p6-b300/trn1/trn2 등(+ UltraServer).
* ⚠️ **HyperPod 타깃은 단일 AZ** — 원문: _"For SageMaker HyperPod clusters: Offerings are limited to a single Availability Zone."_ (Training Jobs는 멀티 AZ 가능.)
* ⚠️ **구매는 취소·수정 불가**(연장만 가능), **계정 간 공유 불가**, 타깃 리소스 유형(HyperPod/Training Job/Inference/Studio)이 **고정**되어 교차 사용 불가.

#### 6.3 Continuous + MinCount

`NodeProvisioningMode=Continuous`(기본 off). all-or-nothing 대신 **컨트롤러 먼저 → 나머지 async 충원**(03 §5.1에 상세). `MinInstanceCount`로 최소 대수를 게이트:

* `MinInstanceCount`는 **0 \~ `InstanceCount`** 범위. `0`(기본)=표준 continuous, `==InstanceCount`=사실상 all-or-nothing.
* Controller·Login 그룹은 **생성 시 기본 1**.
* 3시간 내 MinCount 미달 시 **자동 롤백**(신규 그룹→0,0 / 기존→직전 InService 값).
* ✅ **MinCount는 Slurm·EKS 양쪽 confirmed**(초기엔 EKS 미확인으로 봤으나, EKS continuous 문서에서 동일 파라미터·범위·3h 롤백 확인).

#### 6.4 조합 — FTP + Continuous는 상보적

```
FTP(예약)  →  용량 블록이 "점진적으로" 들어올 수 있음
              └→ Continuous가 잡힌 노드부터 InService (컨트롤러/로그인 우선)
                  └→ MinInstanceCount로 "최소 워커 N대" 되면 학습 시작, 나머지는 async 충원
```

> ❓ **흔한 오해: "FTP랑 Continuous는 둘 중 하나만?" — 아닙니다, 함께 쓰면 궁합이 좋습니다.** FTP는 **물리 용량을 예약**하고, Continuous는 그 용량을 **부분 충원 방식으로 소비**합니다. 예약 용량이 조금씩 들어와도 Continuous가 우선 노드부터 띄우고 MinCount로 최소 워커를 보장하니 잘 맞습니다. FTP 자체는 오케스트레이터 무관하고 **Continuous 없이도**(레거시 클러스터) 쓸 수 있습니다.

> ⚠️ **단, Continuous를 켜면 포기해야 하는 것들**(→ §7): §2 멀티-헤드, §5 `SlurmConfigStrategy`, 온디맨드 deep health check(05 §2.2), 레거시 `provisioning_parameters.json`.

출처: [Flexible Training Plans](https://docs.aws.amazon.com/sagemaker/latest/dg/reserve-capacity-with-training-plans.html) · [Continuous provisioning(Slurm)](https://docs.aws.amazon.com/sagemaker/latest/dg/sagemaker-hyperpod-scaling-slurm.html)

### 7. 상호작용 매트릭스 & 종합 오해 노트

고급 기능은 **서로 배제**하는 조합이 있습니다. 설계 전 이 표를 보세요.

|                    | 멀티-헤드(§2) | Multi-AZ(§3)      | `SlurmConfigStrategy`(§5) | 온디맨드 deep HC | 레거시 `pp.json`    |
| ------------------ | --------- | ----------------- | ------------------------- | ------------ | ---------------- |
| **Continuous(§6)** | ❌ 배제      | ✅ 가능              | ❌ 금지(merge 전용)            | ❌ 미지원        | ❌ 비호환(API 기반 필수) |
| **멀티-헤드(§2)**      | —         | ✅ (주/백업 다른 AZ 권장) | ✅ 가능                      | ✅            | ✅ (주로 레거시로 설정)   |

> ❓ **흔한 오해 ①: "멀티-헤드 HA랑 Continuous를 둘 다 켜면 최강 아냐?" — 동시 불가입니다.** 검증된 원문: _"not currently supported with continuous provisioning on Slurm clusters: **multi-head node configuration via API-based Slurm topology**, and SlurmConfigStrategy."_ **HA(멀티-헤드)를 유지하려면 Continuous를 포기**하고, Continuous의 유연한 프로비저닝을 원하면 **단일 컨트롤러**로 가야 합니다. (근거·인과는 03 §5.1.)

> ❓ **흔한 오해 ②: "커스텀 AMI는 EKS 전용 아니었어?" — 2026-07부터는 아닙니다, Slurm도 명시 지원됩니다.** 이전엔 커스텀 AMI 빌드·관리 문서가 전부 EKS 기준으로 보였지만(구버전 예제가 `HyperPod EKS` 접두·`Orchestrator: Eks`), 현재는 **Slurm이 대등하게 문서화**돼 있습니다:
>
> * 콘솔에서 **`HyperPod Slurm`** 접두로 base AMI를 검색.
> * 최신 base AMI ID 조회 SSM 경로가 Slurm 전용으로 따로 존재: `/aws/service/sagemaker-hyperpod/ami/x86_64/slurm-ubuntu-22.04/latest/ami-id`.
> * CLI 예제도 `--orchestrator 'Eks={ClusterArn=...}'` 대신 **`--orchestrator 'Slurm={}'`** 로 그대로 바꿔 쓸 수 있음(원문: _"Both orchestrators use the same values for the other fields, including `ImageId`"_).
> * 지정 시점: `CreateCluster`(신규 클러스터) 또는 `UpdateCluster`(인스턴스 그룹 추가).
>
> ⚠️ **단, Slurm에만 있는 제약 하나**: `UpdateClusterSoftware`로 **기본 AMI → 커스텀 AMI 전환은 안 됩니다.** 원문: _"For clusters using the Slurm orchestrator, `UpdateClusterSoftware` doesn't support patching from the default SageMaker HyperPod AMI to a custom AMI, including public SageMaker HyperPod Slurm AMIs. To use a custom AMI with Slurm, specify the AMI in `ImageId` at cluster creation, or add a new instance group with the custom AMI using `UpdateCluster`."_ 커스텀↔커스텀 패칭(같은 그룹, 다른 커스텀 AMI로 교체)은 `UpdateClusterSoftware`로 가능합니다 — **"기본→커스텀 전환"만** 안 됩니다. 관련: 03 §2.1의 AMI 기반 라이프사이클(별개 개념 — 커스텀 AMI는 "이미지 자체를 바꾸는" 것, 라이프사이클 방식은 "부팅 후 뭘 설치하나"를 정하는 것)과 혼동하지 마세요.

> 📌 **open question**: 멀티-헤드의 **최대 백업 컨트롤러 개수**는 문서에 명시가 없어 미확인(1 주 + N 백업의 N 상한). 프로덕션 설계 시 AWS에 확인 권장.
